# WiFi-Enabled-Air-Quality-Monitor-and-App
A WiFi Enabled Air Quality Monitor and PC Application based on the Adafruit Air Quality Monitor and Case

Based on the Adafruit: "Air Quality Monitor and Case”,

### Improved? How?  
1) This version puts the monitor on WiFi with a built-in web page and full JSON data dump capability.
2) The original Adafruit version crashes a lot. This has been at least partially fixed in this version so it is more reliable.
3) A full Windows PC Side Monitor Reading Application written in Python is also included.
  
### Changed:  
1) I don’t include the Neopixel strip that the original Adafruit Design used to display the Air Quality Index.
2) The display is not as 'pretty' as the Adafruit design. Just the basics here.
  
### Reliability and Hardware
Reliability was the first issue. The original design hangs a lot. It was discovered that the PMSA003I Air Quality Sensor would hang the I2C bus by locking up and holding the SDA line low. Analyzing the I2C packets for some sort of anomaly did not turn up any issues with the I2C drivers themselves and all available Circuit Python I2C drivers were tried with the same result. The root cause appears to be in the PMSA003I itself. If the SDA line is held low by the I2C device, this in turn causes an exception in the various Adafruit Circuit Python I2C drivers that I tried, including a custom one that I wrote myself. The problem is that the drivers crash the Circuit Python session before any exception can be caught. So using Try/Except to catch the issue won’t work. The ‘hack’ solution is to use circuit pythons Watchdog Timer to restart the monitor when the hangup occurs. This has proven very reliable in at least restarting and keeping the monitor online for most of the time. The monitors I currently have can run for a day without a reset or sometimes they reset in an hour. It is very random. The only real downside of letting the processor reset is that you can’t reliably save any data history on the device itself. For that you will need to use something like Adafruit IO or as I have done – I use a Raspberry PI, which is very reliable, get and store data from the monitor for longer term archiving.  

As a side note: On my outdoor version of the Monitor I use a Sensirion SPS30 Particle Monitor on I2C and it runs and runs, never hanging up. So if utmost reliability is required you might consider that option. There is a Circuit Python driver for the SPS30, so it is an easy switch, although this sensor won't directly fit in the Adafruit Case and it needs 5 volts to run.
  
### Reliability WiFi
Reliability on WiFi is another issue. While it would be nice to be able to use an actual descriptive ‘Hostname’ for discovery on a typical WiFi network, this has proven to be problematic with current hardware and software stacks. While my Raspberry Pi’s will easily accept a hostname and broadcast it correctly on all the WiFi networks I have used, this is not the case with any of the Circuit Python boards I have tied. While the code here uses mDNS as a host name, and it works for a while on my networks, after a period of inactivity all my Windows PC’s seem to forget the name and need to be rebooted to get it back again. The other issue is that every single IP Scanner I have used will not correctly report the mDNS hostname, yet these same scanners easily find all my Raspberry PI’s reliability.
  
The solution is to use the boards MAC address instead. This works reliably and consistently in my experiments. With Circuit Python there is a “boot_out.txt’ file that is generated by the device in the root directory that lists the specific devices MAC address so it is readily found. The PC Client App presented here uses the MAC address to find the current IP address when talking to the device. 
  
What if none of this is reliable for your location, routers, etc? Well, then I suggest that you configure your router to give you a fixed IP address – this has to work. Then you can just address the monitors with a fixed IP address. This will require some reworking of the Monitor Client App, but it is easy enough to do.
  
### Monitor Server Software – Circuit Python
The basis of the software here is the Adafruit code, but with enhancements. For one thing I have decoupled the business logic into sections that can be swapped without having to re-write a bunch of different modules. The sensors have their own module, as does the display. This code division is useful because I have a version of this monitor that does not have a display for outdoor use. So I can just stub out the few display routines with a ‘pass’ and likewise just rewrite the sensors module because the outdoor version uses different sensors – yet the rest of the code can remain exactly the same. 
  
code.py contains the main loop that controls the WiFi connection and requests, the timing to update the sensors and the built-in display, etc. plus all the Circuit Python housekeeping (watchdog, etc). This was chosen because this is the most time critical part of the code if the device is to be responsive to WiFi requests, the requests code are located in the big loop here. The sensors and display are only updated once every 10 seconds (timing easily adjustable in code.py).
  
The AQM Server also spits out data to the power/serial connection on every sensor read for tethered operation. This data is easy to read and parsed by nearly any PC that suports the USB to Serial COM port software (i.e. Windows 10 and 11).
  
There are additions to the settings.toml file for this Monitors code. In addition to the standard WiFi network and password settings, the following settings should be added as shown below. The first addition is the name that the Monitor should use for the mDNS Hostname. This setting must be included or the code will not work. Optional settings are for various sensor offset calibrations. If these settings are not found they will default to zero, so the offsets can be considered as optional. The offsets ‘add’ to the raw reading. So if you add a humidity offset of +2 percent, the data produced by the monitor will show the humidity as being +2% higher on the output. The temperature of the Monitor is typically 5 Degrees C or so higher than ambient due to self heating so at a minimum the temperature offset calibration should be considered.

### PC Side App
The PC Side App is also written in Python 3.12 and uses either PyQt5 or 6 for the GUI. The App reads the Monitor Via WiFi to get the JSON data and display it. To find the Monitor there is an 'ini.py' file that has a dictionary of Monitor names and the Monitors specific MAC address.   
  
![App Data Tab](https://github.com/Hagtronics/WiFi-Enabled-Air-Quality-Monitor-and-App/blob/main/images/screen_shot_1.PNG)
#### Monitor Basic Data Tab shows just the basics.  

![App Details Tab](https://github.com/Hagtronics/WiFi-Enabled-Air-Quality-Monitor-and-App/blob/main/images/screen_shot_2.PNG)
#### The App details tab shows all the JSON data from the monitor as a table.  

To find a Monitor the program first looks at the Windows ARP cache. This cache holds recent MAC addresses and their currently assigned IP address. This cache is dynamic and managed by Windows. If the cache gets old it can be refreshed by a Ping operation. If the specific Monitors MAC address can’t be found in the ARP cache, then the program will scan all the addresses in the range – 192.168.68.1 to 192.168.68.254 as this is the range that most WiFi routers use for assigning devices. This scan range can be changed in the code as needed.
If for some reason your network still gives you trouble and you can’t reliably find the MAC address then I suggest that you configure your router for static IP addresses for the Monitors.

The App will happily keep trying to get data from a previously connected Monitor even if it is taken off line. When the Monitor re-appears on the network, then the App will continue to retrieve data from the previously found IP address.

If the monitor goes missing for more than 10 minutes the App will start rescanning the network looking for the specified MAC address again. This has proven a reliable method of keeping the App alive even after the Monitor is unpowered, moved to another location where it may get a different IP address.
